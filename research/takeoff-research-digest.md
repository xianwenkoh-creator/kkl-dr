# RESEARCH DIGEST FOR THE KKL TAKEOFF SYSTEM DESIGN PANEL (7 topics)

### Extracting measurable geometry from the drawings KKL receives (PDF vector, PDF scanned, DWG/DXF, IFC)
Four input routes, in descending order of what they give for free. (1) DXF/DWG is the only route where quantities are already explicit: ezdxf 1.4.4 reads DXF (never DWG) and returns layers, INSERT block references (count = symbol count), LWPOLYLINE/HATCH boundaries (length via ezdxf.path.make_path + flattening, area via ezdxf.math.area), DIMENSION.get_measurement(), $INSUNITS and paper-space VIEWPORT scale (view_height / height). A local test reproduced a 50.7 m pipe run to 0.003 %, a 400 m2 hatch with a 20 m2 island exactly, and a 1:500 viewport. DWG needs a converter: ODA File Converter (freeware, but ODA says non-commercial only for non-members), LibreDWG (GPLv3, reads all versions, has a WASM npm build), or Autodesk APS Model Derivative (DWG = "simple job", 0.1 Flex token, roughly US$0.30). Civil 3D objects arrive as ACAD_PROXY_ENTITY and only their proxy graphics survive. (2) Vector PDF is what KKL mostly gets. PyMuPDF 1.28 page.get_drawings() returns per-path dicts with items ('l','c','re','qu'), stroke/fill colour, width, dashes, layer (OCG name) and, with extended=True, clip/group hierarchy; get_text('dict') gives text with a per-line direction vector, so rotated dimension text is recoverable. It handled 120,000 segments in 2.4 s (get_cdrawings 0.85 s); pdfplumber took 12.5 s. pdf.js 6.3 exposes the same data in the browser via getOperatorList (OPS.constructPath = 91 with a Float32Array path buffer; OPS.beginMarkedContentProps = 70 carries the OCG id) but you must track the CTM yourself. Tests on real LTA Standard Details of Road Elements PDFs showed the pitfalls concretely: no layers (re-saved through PDFill), 400 to 15,000 paths per A3 page, line weights clustered at 0.36/0.72/1.08 pt, several scales on one sheet (1:20, 1:25, 1:10, 1:50, 1:1000), whole pages where every character is a glyph outline (SHX text exported as geometry, zero extractable words), and rotated pages. A crude dimension-string voting heuristic recovered the declared scale on two of four pages only; scale must be resolved per viewport, with dimension lines detected, and confirmed by a human. (3) Scanned PDFs need raster tooling: centreline tracing (autotrace) rather than Potrace outlines, or deep vectorisation (86 % IoU on floor plans, minutes per sheet), plus OCR that handles rotation (PaddleOCR with textline orientation; Tesseract weak). Multimodal LLMs read dimension text well (Gemini 2.5 Pro about 80 % full-field accuracy on mechanical drawings; Claude Opus 4 about 40 %) but count symbols poorly (0.40 to 0.55). (4) IFC: IfcOpenShell 0.8.5 gives Qto_* sets and computed volumes in a few lines, but IFC-SG/CORENET X is a building-permit regime (BIM only for GFA >= 5,000 m2); LTA street-works submissions are still A1/A3 drawings and LTA rail drawings are MicroStation-origin, so IFC will stay rare for KKL's scope.
Key findings:
- [high] PyMuPDF 1.28.2 page.get_drawings() returns, per path, exactly these keys: closePath, color, dashes, even_odd, fill, fill_opacity, items, layer, lineCap, lineJoin, rect, seqno, stroke_opacity, type, width; items are tuples ('l', p1, p2), ('c', p1, p2, p3, p4), ('re', rect, orientation), ('qu', quad); type is 's' (stroke), 'f' (fill) or 'fs'. get_drawings(extended=True) adds 'clip' and 'group' entries carrying 'level' and 'scissor' so clipping regions (e.g. viewports) can be reconstructed. get_cdrawings() returns the same data as plain tuples and is about 3x faster.
- [high] PyMuPDF exposes PDF layers (Optional Content Groups) fully: doc.get_ocgs() -> {xref: {name, intent, on, usage}}, doc.layer_ui_configs(), doc.set_layer_ui_config(number, PDF_OC_OFF/ON/TOGGLE), doc.get_layer()/set_layer(); each path from get_drawings() carries the OCG name in 'layer'. Turning a layer off hides its paths from get_drawings() AND its text from get_text().
- [high] PyMuPDF throughput is adequate for large CAD sheets: 120,000 stroked segments on an A1 page were extracted in 2.39 s with get_drawings() and 0.85 s with get_cdrawings(); rendering the same page at 150 dpi (4967x3509 px) took 0.63 s. pdfplumber (pdfminer.six) took 12.5 s for the same page and its cached object lists are memory-heavy, so it is the wrong engine for hatch-dense drawings, though its object dicts (x0,y0,x1,y1, linewidth, stroking_color, non_stroking_color, dash, path [(op, pt)...], pts, mcid, tag; chars with matrix/upright/fontname/size) are convenient for small sheets.
- [high] In the browser, pdf.js (pdfjs-dist 6.3.289 current) exposes the same geometry through page.getOperatorList() -> {fnArray, argsArray}. Path data arrives as OPS.constructPath (91) whose args are [paintOp, [Float32Array pathBuffer], minMax]; the buffer is a flat sequence of DrawOPS codes (moveTo 0, lineTo 1, curveTo 2, closePath 4) and coordinates. Layer membership comes from OPS.beginMarkedContentProps (70) / endMarkedContent (71) whose OCG id maps to a name via page.getOptionalContentConfig().getGroups(). Graphics state must be tracked manually: OPS.transform (12), save (10), restore (11), setLineWidth (2), setDash (6), setStrokeRGBColor (58), setFillRGBColor (59), clip (29), eoClip (30).
- [high] Real LTA Standard Details of Road Elements PDFs (kerbs, drains, pavements) are vector but carry no layers, and on several pages all text is stroked/filled glyph outlines with zero extractable words; multiple scales appear on one A3 sheet; pages are rotated; line weights cluster at 0.36/0.72/1.08/1.44 pt.
- [high] AutoCAD exports SHX-font text as geometry, not text; since AutoCAD 2016 the PDFSHX variable can add hidden 'AutoCAD SHX Text' comments so it becomes searchable, and TrueType fonts stay as real text. Layers reach the PDF only if 'Include layer information' is enabled in the DWG To PDF.pc3 custom properties; PDF layers apply to the whole page, so per-viewport layer states (VPLAYER) are not represented. Hatch patterns export as one vector primitive per hatch line/dot and can add tens of MB to a PDF.
- [medium] Automatic scale detection from dimension strings works but must be done per viewport, not per page: a simple heuristic (numeric word adjacent to a horizontal segment, vote for implied scale) recovered the declared scale on 2 of 4 LTA detail sheets (kerb sheet 1:20 with 23 votes; drain sheet 1:20 with 6 votes) and failed on two detail-dense sheets where 1:100/1:30 votes outnumbered the declared 1:25.
- [high] ezdxf 1.4.4 gives earthworks-relevant quantities directly from DXF: msp.query('INSERT[name=="SUMP_600"]') counts block references; ezdxf.path.make_path(entity).flattening(1.0) + ezdxf.math.ConstructionPolyline(...).length gives polyline/arc length; ezdxf.path.from_hatch(hatch) yields boundary loops (paths.external_paths(), outermost_paths(), has_pattern_fill) whose area comes from ezdxf.math.area(); Dimension.get_measurement() returns the true WCS measurement while dxf.text holds the override ('<>' or '' = measured value, any other string = override); Viewport.dxf.view_height / dxf.height gives the plotted scale; doc.header['$INSUNITS'] gives units (4 = mm, 6 = m); ezdxf.bbox.extents() gives drawing extents.
- [high] DWG must be converted before ezdxf can read it, and the licensing differs: ODA File Converter (ezdxf.addons.odafc.readfile/convert/export_dwg, R12 to R2018, needs xvfb on headless Linux) is freeware but ODA states non-members may use it for non-commercial applications only; LibreDWG (GPLv3) reads all DWG versions with some advanced R2010+ objects skipped, writes reliably only up to R2000, and ships dwg2dxf, dwgread, dwg2SVG, plus a WebAssembly npm build (@mlightcad/libredwg-web 0.7.10) that parses DWG in the browser.
- [medium] Autodesk APS Model Derivative is a paid cloud alternative for DWG: since 8 Dec 2025 translation is billed in Flex tokens, 0.1 token per 'simple' job (DWG, anything not Revit/IFC/Navisworks) and 0.5 per 'complex' job, with a free monthly allowance; Flex tokens retail at about US$3 (2021 list price), i.e. roughly US$0.30 per DWG. Output exposes DWG layers as objects in the object tree with bounding boxes and properties, and 2D sheets as F2D viewables.
- [high] Civil 3D content (surfaces, alignments, pipe networks, AeccDb* objects) does not survive as semantic data in DXF: it arrives as ACAD_PROXY_ENTITY, and ezdxf can only recover the proxy graphic via virtual_entities() or explode() ('the meaning and data of this entity is lost'). The originator must run EXPORTC3DDRAWING / Export to AutoCAD, and surfaces should be requested as LandXML for cut/fill.
- [high] Singapore's CAD layer standard is SS CP 83-1:2004 (2020, Amendment 1 March 2026), derived from ISO 13567, with fields originator / element / sub-element / presentation / status; BCA and HDB adopted it for electronic submissions, NTU requires it for as-builts, and LTA's Civil Design Criteria clause 1.6.6.1 requires drawings to comply with 'Drawing and CAD Standard (Microstation) and SS CP83' while 1.6.6.2 points BIM to the Singapore BIM Guide and project-specific LTA BIM Requirements. LTA rail drawings are therefore MicroStation (DGN) in origin; DWG/DXF reaching KKL are conversions.
- [high] IFC is straightforward to quantify with IfcOpenShell 0.8.5 but will be rare for KKL: ifcopenshell.util.element.get_psets(el, qtos_only=True) returns Qto_* sets (e.g. {'Qto_WallBaseQuantities': {'NetVolume': 3.0, 'Length': 5.0}}) and ifcopenshell.geom.create_shape(settings, el) + ifcopenshell.util.shape.get_volume / get_footprint_area / get_x/y/z / get_footprint_perimeter recompute quantities from geometry; IFC4X3_ADD2 (IfcEarthworksCut/Fill, IfcAlignment, IfcRoad) parses, but IfcOpenShell's extensive geometry support is for IFC2x3/IFC4.
- [high] CORENET X / IFC-SG is a building-permit regime, not a civil-works deliverable: mandatory for new projects with GFA >= 30,000 m2 from 1 Oct 2025, all new projects from 1 Oct 2026, ongoing projects onboarded from 1 Oct 2027 without IFC+SG; BIM submissions are required only for GFA >= 5,000 m2. LTA's 15 Sep 2025 street-works circular still specifies drawings 'to be A3 / A1 size' with SDRE references, and LTA's 43 IFC-SG parameters concern development-related access, parking and external works. Infrastructure works do route through CORENET X gateways (LTA, PUB, NParks) but no IFC requirement for public roadworks/drainage was found.
- [medium] For scanned sheets, outline tracers (Potrace, Inkscape Trace Bitmap) produce double lines around each stroke and are unsuitable for measurement; centreline tracing (autotrace -centerline, skeletonisation + tracing + curve fitting) is required and degrades sharply when scan quality breaks pixel connectivity. Deep vectorisation (Egiazarian et al.) reaches 86 % IoU and 0.2 px mean deviation on 2000x3000 px floor plans but needs 5.5 to 12 min per image for high accuracy; a 2026 hybrid DL + rule-based method targets scanned architectural drawings. An A1 sheet at 300 dpi is about 9,900 x 7,000 px.
- [medium] OCR of dimension text on drawings is the weak link: Tesseract handles clean horizontal text only; PaddleOCR is strongest among open engines on rotated text but its detector normalises box corner order and needs use_textline_orientation enabled (and fine-tuning) for 90-degree dimension text; Azure Document Intelligence is judged unsuitable for dense drawings. Multimodal LLMs read dimensions unevenly: on 10 mechanical drawings with 17 to 58 dimensions each, Gemini 2.5 Pro scored 80.0 % full-field accuracy, Gemini 2.5 Flash 77.3 %, Claude Opus 4 40.5 %, GPT-4o mini 39.6 %; AECV-Bench finds symbol counting (doors/windows) at only 0.40 to 0.55 accuracy while text QA reaches 0.95.
- [high] Commercial and open takeoff tools confirm the architecture: Kreo accepts PDF, DWG, DXF, DWF, DGN and images and reads native vector data; Togal.AI is PDF floor plans only; civils.ai claims >97 % on modern PDFs but only with human QA and lists cut/fill as 'coming soon'; AGTEK states fully automatic earthworks takeoff 'is currently not realistic' and positions AI for linework cleanup, text extraction and sheet alignment/scaling. OpenTakeoff (Apache-2.0) is a working reference implementation: pdf.js rendering, flood-fill room detection on PDF vector linework with raster fallback (adaptive threshold, gap bridging), CAD layer tree used to separate boundaries from annotation, auto-detected scale note, and a 'check a dimension' grader (green within 1 %, amber within 5 %), exposed as 47 MCP tools.
- [high] Round-tripping and rendering tools exist to validate extraction: ezdxf's drawing add-on has SVGBackend and PyMuPdfBackend (PDF/PNG from DXF, get_pdf_bytes(layout.Page(...))), which lets a synthetic DXF with known quantities be rendered to PDF and re-measured through the PDF pipeline; AutoCAD's PDFIMPORT converts vector PDF back to DWG (layers prefixed 'PDF_', SHX text recognition, coordinate rounding), and Poppler's pdftocairo -svg / pdftotext -bbox-layout give a second independent vector and text-position extraction.
Implications:
- Build one internal geometry model (per sheet: viewports with scale + unit, layers, paths with width/colour/dash, text with position and direction, images) and feed it from three importers: PyMuPDF (server) or pdf.js getOperatorList (browser) for PDF, ezdxf via DXF for CAD, IfcOpenShell for the rare IFC. All takeoff logic (length/area/count/classification) then runs on the same model regardless of source.
- Use PyMuPDF get_cdrawings()/get_drawings(extended=True) as the primary PDF extractor (0.3 s per dense A3 sheet, clip hierarchy for viewports, OCG layer per path); keep pdf.js only for on-screen snapping in the single-file web app, and pin the pdfjs-dist version because constructPath argument packaging changes between releases.
- Treat scale as a first-class, per-viewport object that must be confirmed by the QS: seed it from title-block text ('SCALE 1:20', '@ A1') and page size (A1 = 2384x1684 pt, A3 = 1191x842 pt), refine from detected dimension strings, and store the confirmation as training data; never apply one page-wide scale to LTA-style detail sheets that mix 1:10 to 1:1000.
- Expect no PDF layers from clients: the LTA standard drawings had none after re-save. Classify linework instead by stroke width (0.36/0.72/1.08/1.44 pt pens), colour, dash pattern and proximity to labels, and let QS corrections train that classifier; KKL's activity codes (DR-PIPE m, RW-KERB m, EW-EXC m3, RC-CONC m3) are the label set.
- Detect 'text as outlines' pages automatically (words == 0 with thousands of small Bezier fills) and route them to OCR/vision on a 300 dpi render; ask clients/main contractors for PDFs plotted with TrueType fonts or PDFSHX=1 and 'Include layer information' enabled, and for DXF/DWG where possible, because each of these removes a whole class of errors.
- Ask for DXF/DWG (or DGN converted) on MRT and LTA contracts; from DXF, block counts (sumps, manholes, lamp posts), polyline lengths (pipes, kerbs, drains), hatch/closed-polyline areas (excavation, hardcore, sub-base) and DIMENSION measurements come out exactly, which makes DXF the fastest route to 'machine takes over' for counts and lengths.
- Choose the DWG converter by licence: LibreDWG (GPLv3, in-process or WASM in the browser) for an internal tool; ODA File Converter only after confirming commercial-use terms; APS Model Derivative (about 0.1 token per DWG) when the volume is small and cloud upload is acceptable.
- When a client drawing came from Civil 3D, request Export-to-AutoCAD DXF plus LandXML surfaces; contours and spot levels traced from PDF should be used only for area/length, with cut/fill volumes computed from surfaces (existing vs proposed TIN), which is also what civils.ai and AGTEK say is required.
- For scanned sheets, do not attempt full vectorisation in phase 1: render, OCR with rotation handling (PaddleOCR with use_textline_orientation, or a vision LLM for dimension text), let the QS trace with snapping to a centreline skeleton, and record every trace as labelled data for later automation.
- Adopt the OpenTakeoff-style 'check a dimension' grader as the acceptance test for every automated measurement: pick 2 to 3 dimension strings per viewport, compare measured vs printed, and block export when deviation exceeds 1 % (green) / 5 % (amber).
- Do not invest in IFC-SG/CORENET X tooling for earthworks; IFC will appear, if at all, as building-structure models from main contractors, for which IfcOpenShell get_psets(qtos_only=True) plus util.shape functions are sufficient in under 50 lines.
- Build a regression corpus now from real KKL inputs (LTA SDRE sheets, MC-issued PDFs, any DXF received) plus synthetic DXF-to-PDF round trips with known quantities, and measure per-route precision on it before promising any takeoff class is 'taken over'.

### What KKL's QSs actually take off every day, and where the hours go: inventory of takeoff item classes for a Singapore earthworks and drainage contractor
KKL's QS work splits into two measurement worlds that automate differently. (1) Drawing-based takeoff at tender, VO and final remeasure: the primitives are a small set — polygon area (pavement, hardcore, footpath, clearance), polyline length along a run (RC pipe by dia and depth band, U-drain by size, kerb by type, railing, road marking), count with attributes (sumps/DICs/manholes by type and depth-to-invert, scuppers, connections), and volume from levels (bulk cut/fill from spot levels or contours against formation levels; under-strut lifts from plan area × strut-level differences). Everything else — trench excavation, backfill, disposal, bedding, lean concrete, formwork, concrete and rebar for CIS drains/culverts/sumps, asphalt tonnage — is a calculation from those primitives plus standard details (LTA SDRE, PUB COP, M&W trench-width rules) and BQ preambles (measured nett, no working space, no bulking, depth stages). Singapore public-sector BQs (LTA Price Document/SOR, HDB SOR, term-contract FSORs) follow SMM2-style preambles rather than CESMM; item structure is depth-banded m3 for excavation, per-m by size/depth stage for drains and pipes, m2 by stated thickness or tonne for pavement, m3/m2/kg for RC, and nr for chambers. (2) Site-record measurement for monthly SOPA progress claims and subcontractor certification: quantities come from chainage and zone entries in daily reports (KKL's DR Capture already records activity code, IW×depth, chainage, depth band, soil type, spoil destination, loads), survey levels (pre/post DTM or strut-level surveys), disposal trip tickets, concrete delivery orders, rebar delivery/BBS, and weighbridge tickets for asphalt (LTA M&W pays asphalt by weight), then reconciled against BQ/provisional quantities that are admeasured on completion. Estimated hour split for a contractor-side earthworks QS team (inference): tender takeoff 35–45% (bursty), monthly progress claims incl. subcon certification 25–30%, VOs/claims 10–15%, ordering and final-account remeasure 10–15%. Within tender takeoff the heavy blocks are bulk excavation from levels (15–20%), CIS RC drain/culvert build-ups (15%), trench/drain runs and their derived excavation/backfill/disposal (15–20%), pavement areas (5–8%), and BQ entry/reconciliation in Excel (15–20%); counts and schedule reads are under 10% but are the easiest to automate first. Generic industry data say quantification consumes 50–80% of estimating time and manual detailed takeoffs are accepted at 2–5% variance; earthworks volumes by average end area sit within 3–5% of surveyed volumes. Implication for KKL: automate the primitives and the deterministic calculators behind them, keep depth-band/soil-class judgement and level-based volumes under human check, and use the daily-report data as the ground truth loop for progress-claim quantities.

- [high] SG BQ item structure for the classes KKL prices: excavation in m2 for shallow surface strip (avg ≤100/200/300 mm) and m3 above that; pit/trench/basement excavation in m3 by depth band ne 2.00 m, 2–4 m, 4–6 m, extra over per 2 m; pipe/kerb trenches per m by 0.25 m depth stages in term contracts; filling in 150–300 mm layers m3; disposal m3 (bulking in rate); concrete m3 by grade (rounded up to 0.1 m3); bar reinforcement kg by diameter band; fabric reinforcement m2 measured nett; formwork m2; drains per m by internal size and depth-to-invert stage; chambers per nr by depth or m2 internal × depth; pipe fittings 'extra over' per nr; pavement per m2 at stated thickness or per tonne for asphalt with add/deduct per 6 mm.
- [high] LTA standard details fix most of the geometry a QS otherwise has to measure, so many KKL items reduce to length or area × a lookup: precast U-drain sizes 600–1500 wide, depth to 1500, unit length 1.0 m (0.5 m where curve radius <20 m); precast channel/drain units 500 mm long; CIS box culvert wall/slab thickness and T13 reinforcement by size; kerbs K2A/K2B 980 mm units (150/300 mm shorts on sharp radius); flexible pavement layer thicknesses by road type; rigid pavement 225 mm C28/35 with WSFR B8; DICs at 6 m c/c at footpath ramps.
- [medium] The drawing set a KKL QS works from for LTA/PUB drainage and road jobs is: site/layout plan (1:100–1:1000) with kerb alignment and drain alignment + invert levels, longitudinal and cross sections, detail sheets referencing SDRE sheet numbers (1:5–1:20), topographical plan with spot levels, utility plans, TTM/traffic plans; PUB drainage submissions add drainage layout plans, longitudinal and cross-section drawings and hydraulic calculations.
- [medium] Contract form determines what gets remeasured: PSSCOC Option Module A uses BQs with quantities marked 'provisional' for remeasurement contracts; LTA Preliminaries admeasure provisional-quantity items on completion; SOPA drives one payment claim per month with 14-day response, so claim measurement is a fixed monthly cadence per project (KKL lists ~30 live public-sector contracts, so roughly 30 claim packs a month plus subcon certifications — inference).
- [high] Variation-order takeoff is a differential measurement: identify latest drawing revision, highlight changes, measure omissions from the old drawings and additions from the revised drawings, then price in strict order BQ rate → pro-rata → star rate → daywork; on schedule-of-rates contracts BQ quantities must not be used as the basis for omissions.
- [medium] Where the hours go (industry data, not KKL-specific): quantification is 50–80% of estimating time; vendors claim 'estimators spend 80% of their time counting and measuring plans'; manual takeoff ~45 min per 5 plan pages; 85% of construction professionals still estimate in Excel; SG QS postings commonly ask for Bluebeam, AutoCAD, CostX or Cubicost.
- [medium] Accuracy norms a takeoff system should be measured against: detailed bid takeoffs are accepted at 2–5% variance (5–10% for conceptual); manual takeoffs on large sets show 5–10% fatigue error; average-end-area earthwork volumes fall within 3–5% of surveyed volumes and systematically over-estimate by 2–8% vs prismoidal; drone/DTM surveys reach ~3 cm; a 1% quantity error can swing a bid 8–12%.
- [medium] Reinforcement is mostly a document read plus arithmetic, not a drawing measurement: a BBS lists bar mark, size, shape code (BS 8666), cutting length, number, total length and weight; without a BBS QSs use kg/m3 assumptions; BRC/WSFR fabric is measured nett in m2 with kg/m2 lookups that differ by standard (A10 = 6.16 kg/m2 in BCA table vs 7.90 kg/m2 in SG supplier tables), so the mesh reference must be resolved to a specific standard.
- [high] KKL's own daily-report schema already encodes the site-side measurement model the takeoff system must reconcile to: quantities per activity code with unit (m3/m2/m/no/t/load/day/hr), structure type and method (U-drain, covered drain, RCBC, RCS sump/DIC, pipe drain; CIS / half precast / full precast), element (drain wall/base/top slab, benching, sump, pipe surround, box culvert, kerb haunch), IW × depth per m, chainage from/to, depth band, ground, soil type, spoil destination and load counts; the office verifies and edits qty with an audit log.
- [medium] Disposal pricing depends on a takeoff that is really a soil-class split from SI data, not a drawing measurement: SG disposal runs ~S$30–60/m3 by soil type; LTA M&W defines Top Soil, Suitable, Not Suitable, Unsuitable (not Contaminated) and Contaminated material classes; KKL's DR captures soil_type per excavation row; planning defaults elsewhere use swell 35%, shrink 15%.
- [low] Estimated split of KKL QS hours by task (inference, to be validated by a two-week time log): tender takeoff 35–45%; monthly progress claims incl. subcon certification 25–30%; VOs and claims 10–15%; material ordering and final-account remeasure 10–15%; ad-hoc (quotes to MCs, rate build-ups) remainder. Frequency: tenders bursty (weeks-long), claims strictly monthly per project (~30 live contracts), subcon certification monthly per subcon (asphalt, RC, marking), VOs ad hoc, ordering weekly.
Implications:
- Model the takeoff system around four drawing primitives (polygon area, polyline length with attributes, count with attributes, surface volume from levels) plus a deterministic calculator layer; ~60% of KKL's BQ lines (trench excavation, backfill, disposal, bedding, lean, formwork, concrete, asphalt tonnage, kerb haunch) are formulas over those primitives and SDRE/M&W lookups, so they should be generated, versioned and unit-tested as code, never 'measured' by a model.
- Order of automation by risk and share of hours: (1) counts and schedule reads (sumps/DICs by type and depth, pipe schedule, drain schedule, BBS totals, BQ line extraction) — near-exact, JSON-schema extraction with page citations, already prototyped; (2) polyline runs on vector PDFs (pipes by dia/depth band, U-drains by size, kerbs by type) with the long-section supplying IL/GL to auto-band depth; (3) hatch/polygon areas for pavement layers, footpath, hardcore with SDRE road-type thickness lookup; (4) surface volumes from spot levels/contours and strut levels (needs a DTM engine and human check; target ≤3% vs QS); leave existing-condition demolition and soil-class splits as assisted only.
- Encode Singapore preambles as rules in the calculator: measured nett, no working space, no bulking, spot-level constant-gradient assumption, depth bands (ne 2/2–4/4–6 m or contract-specific 0.25 m stages), concrete rounded up to 0.1 m3, fabric nett with no laps, trench length measured over sumps, asphalt by tonne via density; make the band set and rounding a per-contract configuration read from the BQ preambles (Extract agent can pull them).
- Reuse the daily-report data model as the reconciliation schema: every takeoff line should carry activity code, structure type, element, chainage from/to, depth band and soil type so that a tender quantity, a claim quantity (from DR rows, survey, tickets, DOs, weighbridge) and a BQ line join on the same keys; this gives the 'learns from takeoffs they already do' loop and the accuracy ledger without extra data entry.

Across 2024-2026 evidence, the picture is consistent: frontier vision-language models (Gemini 3 Pro, GPT-5.2, Claude Opus 4.5) are good document assistants on drawings (OCR of title blocks, notes, schedules and legends at ~0.9-0.95 accuracy) but are not yet reliable measurers or counters. AECV-Bench (Jan 2026, 120 floor plans) puts the best model at 0.51 mean exact-match on door/window/room/toilet counts with 16% MAPE, and door and window exact-match at 0.39/0.34; Gemini leads, GPT-5.2 is close, Claude and small open models trail. A mechanical-drawing dimension benchmark (Businessware, 2025) shows the same ordering: Gemini 2.5 Pro ~80%, Gemini Flash ~77%, Claude Opus 4 ~40%, o4-mini ~40%, o3 ~20%. Zero-shot GPT-4o/Claude 3.5 on GD&T extraction hit 25-37% recall with up to 56% hallucination, while a fine-tuned 0.23B Florence-2 on 400 drawings beat both by 30-52 points. Tiling helps detail tasks only when a global thumbnail is also supplied (ScienceQA 71.3% to 80.2%), and can hurt text tasks; VLM counting errors grow with density.

Specialised detectors are the reliable path for symbols: YOLOv8 reaches mAP50 82.5% on 34 electrical symbol classes from 45 scanned plans (2,450 instances), and CAD-native panoptic symbol spotting now has a 413k-chunk dataset (ArchCAD-400K) with primitive+image fusion baselines. Floor-plan vectorisation has moved to VLMs that emit JSON polygons (FloorplanVLM, 92.5% external-wall IoU on a 2M-plan corpus), but every one of these datasets is architectural residential; no public dataset exists for civil plan/drainage/road cross-section drawings, and contour extraction from scanned maps remains classical CV plus gap-repair heuristics with scan-quality-dependent accuracy.

Vendors confirm the hybrid pattern. Kreo Auto Measure 3.0 reads native PDF/CAD vectors, runs a second pass that "re-fits every outline to the lines of the drawing", and reports outline accuracy 72% to 94% and captured area 92.6% to 99.3% on rooms/walls/openings, plus prompt-driven object counts. Togal claims "up to 98% on floor plans" from ML trained on "thousands of plan sets" and three patents, all for building trades. Beam AI and Civils.ai both sell AI plus a human QA queue (Beam: "99%+", "within ±1% of in-house", 24-72 h; Civils.ai: "over 97%", 24 h turnaround, $9/takeoff). Nobody publishes independently audited accuracy for money-bearing quantities on civil drawings.

Recommendation for KKL: measure with deterministic geometry (DXF layers/blocks, vector PDF paths, as the repo spikes already prove exact), use VLMs for classification, legend/schedule/title-block reading and cross-checking, use small fine-tuned detectors for recurring symbols on scans, and keep a QS confirmation step with per-class accuracy tracking that gates progressive automation. Cross-sections, contours and earthwork volumes from scanned sheets stay human-led with AI assistance for the foreseeable future.
Key findings:
- [high] Frontier VLMs still cannot count drawing symbols reliably: on AECV-Bench (120 floor plans, doors/windows/bedrooms/toilets) the best model, Gemini 3 Pro, reaches only 0.51 mean exact-match accuracy with 16.0% mean MAPE; GPT-5.2 0.49 / 19.4%; door and window exact-match for Gemini are 0.39 and 0.34. Text-centric drawing QA (OCR of notes, title blocks, schedules) reaches 0.70-0.95, spatial reasoning ~0.6-0.78, and instance counting is the weakest QA category. Authors conclude counting features must ship as assistive, human-in-the-loop tools.
- [medium] On dense dimensioned engineering drawings the model ranking is Gemini >> Claude ~ GPT-mini > o3, and absolute accuracy of the best is ~80%: Gemini 2.5 Pro ~80%, Gemini 2.5 Flash ~77%, Claude Opus 4 ~40%, o4-mini ~39.6%, o3 ~20%, Qwen VL Plus ~8% on 10 real mechanical drawings with 17-58 dimensions each (a dimension counts only if all nine fields incl. view, type, nominal, tolerance are right). Failure modes: geometric tolerances, mixed one/two-sided tolerances, wrong view assignment (Claude, Qwen), whole sections omitted (Qwen).
- [high] Zero-shot frontier VLMs have low recall and high hallucination on structured extraction from drawings, and a small fine-tuned open VLM beats them: GPT-4o precision 59.03% / recall 25.39% / F1 35.51%; Claude 3.5 Sonnet precision 44.01% / recall 37.27% / hallucination 55.99%. Florence-2 (0.23B params) fine-tuned on 400 expert-annotated drawings improved precision +29.95 pts, recall +37.75, F1 +52.40 and cut hallucination by 43.15 pts vs the best closed model. Recall falls and hallucination rises as the number of entries per drawing grows.
- [high] Tiling large drawings into crops helps VLMs on detail-oriented tasks only when a global (thumbnail) view is also provided; it hurts text/OCR and conversational tasks and 3x3 without global context degrades hallucination metrics. Reproduction of Monkey-VLM tiling: ScienceQA-Img 71.34% -> 80.17% (3x3 + global), POPE F1 78.57% -> 81.86% (2x2), TextVQA 52.99% -> 49.96% (below baseline even with global), LLaVA-Bench worse for every tiling. Adding global context costs only 5-12% extra compute. Related 2025 work (CropVLM, ZoomEye, Zoom-Refine) shows model-driven zoom-in gives modest 2-5% gains.
- [high] Fine-tuned single-stage detectors are the practical tool for symbol counting on scanned plans: YOLOv8 reaches mAP@50 82.5% (avg mAP 81.1%) on the DELP dataset of 45 scanned electrical layout plans, 2,450 instances, 34 service-key classes, versus Faster R-CNN 48.6%; outputs are per-class counts feeding cost estimates. Reviews of engineering-diagram digitisation concur YOLO-family beats two-stage detectors on drawings; few-shot and semi-supervised P&ID symbol detection are active 2024 topics because labelled data per symbol set is scarce.
- [high] Public drawing datasets are architectural, not civil. CubiCasa5K: 5,000 CAD-derived floor plans with SVG annotations, 80+ classes (rooms + icons), multi-task segmentation/detection. ArchCAD-400K (2025): 413,062 chunks from 5,538 standardised CAD drawings, annotated automatically from CAD attributes (26x larger than prior CAD symbol datasets), with a Dual-Pathway Symbol Spotter baseline that fuses vector primitives with raster features. RPLAN is a residential layout-generation dataset (~80k plans). No public dataset for drainage plans, road plans, long-sections, cross-sections or earthworks drawings was found; civil 'datasets' in 2024-26 are crack/road-surface imagery, LiDAR or satellite, not drawings.
- [medium] Floor-plan vectorisation has moved to VLMs that emit structured vector JSON: FloorplanVLM (Feb 2026) frames vectorisation as image-conditioned sequence modelling, trained on Floorplan-2M and Floorplan-HQ-300K with SFT then GRPO, reporting 92.52% external-wall IoU on FPBench-2K and handling slanted/curved walls. SAM is used as a zero-shot segmenter for rooms/areas with GPT-4 as classifier (SAM proposes masks, contour detection makes polygons), and FloorSAM applies it to LiDAR density maps. Results are for buildings; no equivalent for civil sheets.
- [medium] Contour-line extraction from scanned maps is still mostly classical CV (colour segmentation e.g. spatial fuzzy c-means, thinning) plus gap repair; a Dec 2024 paper reconnects broken contour segments by endpoint matching on Euclidean distance and gradient direction then cubic Hermite spline interpolation, and a Dec 2025 IJGI study of deep-learning contour vectorisation finds moderate reductions in scan quality do not materially change accuracy. No 2024-26 source reported DEM RMSE for AI-derived contours from construction drawings; results are for topographic map sheets, not site survey plans.
- [high] Kreo's Auto Measure 3.0 is the clearest public description of the 'AI classifies, geometry measures' hybrid: it reads native PDF and CAD vector data, a first pass finds rooms/walls/finishes/openings, a second pass 're-fits every outline to the lines of the drawing', and users prompt for custom objects to count (e.g. 'parking bays'). Scope is building plans; no civil/site categories. Kreo also exposes an Auto Measure API.

Caveat: synthetic sheet had no curves, hatching, overlaps or multiple viewports.
- [medium] Inference: 'solved enough to automate with verification' for KKL = reading title blocks/scale/revision, legends, schedules and BQ text (VLM OCR ~0.9-0.95, verify with scale bar and totals); measuring lengths/areas/counts from DXF layers/blocks and vector-PDF paths once a class mapping exists (deterministic, exact). 'Hybrid' = classifying which paths/layers are which BQ item, matching labels to runs, counting recurring symbols on scans (fine-tuned YOLO, expect 80-90% mAP, human confirms), area polygonisation on scans, drawing-revision diffs. 'Stay manual (AI-assisted)' = earthwork volumes from cross-sections/contours on scanned sheets, under-strut/top-down excavation staging quantities, judgement items (working space, bulking, disposal classification), anything where a VLM count is the only source.
Implications:
- Architecture: VLM classifies and reads, code measures, QS confirms. Never let a VLM-emitted number become a quantity; VLM output should be a class label, a legend mapping, a region of interest, or a cross-check, while lengths/areas/counts come from DXF entities, PDF path geometry or a detector over a scan.
- Input hierarchy for KKL: push clients/main contractors for DWG/DXF (exact, layered, blocks), then vector PDF (exact after scale/legend/class mapping), then 300 dpi+ scans (2% band, needs OCR + detector), and treat sub-200 dpi scans as not fit for money-bearing quantities.
- Training data flywheel: every QS confirmation/correction of a class mapping or symbol count is a labelled example. Store (sheet, region crop, path signature or block name, BQ code, QS decision). Fine-tune a small detector (YOLOv8/11) per recurring symbol set (sumps, manholes, kerbs types, sign posts) once ~40-50 sheets / ~2,000 instances per family exist, matching SkeySpot scale; expect mAP50 in the 80s, so always show confidence and let a human accept.
- Progressive automation gate: per activity code (EW-EXC m3, DR-PIPE m, RW-KERB m, RC-CONC m3) track auto-vs-confirmed error on a rolling window; move a class from 'AI proposes, QS confirms' to 'auto with sample audit' only when error is within the QS's own tolerance (e.g. 1-2% on lengths/areas, exact on counts) over N sheets. This mirrors what Kreo and Beam publish as coverage/retention metrics.
- Use tiling deliberately: for VLM reads of large A1/A0 sheets send a global thumbnail plus crops (2x2/3x3 with overlap), route OCR-like questions to full-sheet images and detail/count questions to crops, and reconcile counts with geometry-derived counts rather than trusting either alone.
- Model choice: benchmark Gemini 3 Pro / GPT-5.x / Claude Opus 4.5 on KKL's own sheets before committing; evidence shows Gemini currently leads on dense drawing reads, and the existing Claude workbench is fine for text/schedule/legend/citation tasks but should not be the counting engine.
- Cross-sections and contours: build a semi-automatic tool (user picks datum/scale, code extracts polylines from vector sections, computes end-area volumes) rather than an AI recogniser; for scanned sections, AI can only assist with line tracing and gap repair, and the QS keeps ownership. This is where the largest earthworks money sits and the least published accuracy exists.
- Aerial-to-CAD (Airworks-style U-Net segmentation of orthomosaics/point clouds into layered DXF) is a separate, more mature route for existing-ground and as-built quantities than drawing understanding; consider pairing drone survey with drawing takeoff for cut/fill progress claims.

### Takeoff tools QSs use today and how to plug into them to capture daily takeoffs as training data (Bluebeam, Kreo, Togal, STACK, PlanSwift, OST, CostX, Cubit, Trimble, Kubla, TBC, Civil 3D, 12d, Carlson, Propeller, DroneDeploy, generic PDF tools; SMM support)
The single cheapest, zero-behaviour-change source of ground truth is the marked-up PDF itself. Bluebeam Revu (the de facto QS tool; Basics US$260, Core US$330, Complete US$440, Max US$590 per user per year) stores every measurement as a standard PDF annotation (Line /L, PolyLine and Polygon /Vertices, Rect) with an ISO-32000 /Measure scale dictionary and Bluebeam-private keys (/Subj subject, /BSIColumnData custom columns, layer via optional content). pypdf and PyMuPDF read these keys as ordinary dictionary entries, so a nightly job that walks the tender/claims folders on SharePoint (Graph delta query) or a network share, opens each new or changed PDF, and logs (sheet, page label, scale, annotation subtype, vertices in page units and metres, subject, label, layer, author, date, measured value) captures geometry + scale + item name for every takeoff a QS does, with no change in how they work. The same extractor covers Acrobat, Foxit and PDF-XChange measurement annotations. Bluebeam's own exports are weaker: the Markups List Summary to CSV/XML carries values, subject, layer, page label, X/Y position and count but not vertices; BAX/FDF carry the annotations but are for transfer, not reporting; the Developer Portal (free with Core+) exposes Studio Projects/Sessions and a Markups API that reads/updates status, not geometry, but it can download the PDFs. Quantity Link (Complete) live-links totals to Excel cells and shows where QS BQ workbooks already hold item-to-quantity mappings.

Among AI takeoff SaaS, Kreo (US$35/70/175 per month; API on Pro by request and full API on Enterprise, including measurement extraction; Excel in/out from Plus) is the only affordable one with a documented API that returns measurements. Togal.AI (about US$199 to 299 per user per month, quote-based) exports Excel only and has no data API. STACK (US$2,599 per year Takeoff & Estimate) has a partner REST API returning quantities, items and plans, not vertices. PlanSwift (US$1,749 one-off plus US$250 per year) has a COM/scripting API and Excel linking; On-Screen Takeoff is quote-based with Excel condition links only. QS estimating suites CostX (quote), Cubit (A$167 to 250 per user per month; BOQ only in Professional and above) and Trimble Quest/B2W (quote) are Excel-centric with no public API. Earthworks volume tools (Kubla Cubed US$295 per year, Carlson Takeoff US$1,800 per year or US$7,500 perpetual, TBC Construction bundle about A$6,730 per year, Civil 3D, 12d) exchange surfaces via LandXML/DXF and volumes via CSV/Excel; drone platforms (Propeller, DroneDeploy from US$4,188 per year) expose APIs and CSV volume reports. Earthworks volume is a surface-difference problem, not a drawing-tracing problem. The three classical methods rank clearly: average-end-area (cross sections at intervals) systematically over-estimates, typically 5–10% (one field study: +6.8% at 25 stations); the prismoidal formula removes most of that; and TIN/DTM surface-to-surface (Civil 3D "composite", CloudCompare 2.5D, PDAL/GDAL raster difference) is the most accurate provided the input surfaces are good. So the takeoff system's target representation for bulk earthworks is two surfaces (existing and design) plus a boundary, and the volume becomes deterministic code. Inputs that already contain surfaces (LandXML <Surface> = point list + triangle list, readable with lxml or the QGIS LandXml plugin; DXF 3DFACE/contours via ezdxf; drone DSM/LAS via PDAL) give exact volumes; PDF contour drawings need contour vectorisation (vector PDF: read polylines and attach the elevation labels; scanned: U-Net contour segmentation is the 2025 research state of the art, 2.5% not yet turnkey) then TIN generation (GDAL gdal_grid / scipy Delaunay) with an accuracy penalty that must be measured per drawing type.

Trench and pit excavation for drains, culverts, sumps and manholes is a calculation over the drawing data the vector-PDF spike already extracts: run length × trench width (pipe OD + working space per the contract preamble) × depth from invert/ground levels, split into depth bands (CESMM/HK CESMM style "maximum depth not exceeding 3 m, 3–6 m, then 3 m steps"), less backfill volume occupied by the pipe/structure. The rules that govern this are contractual: HK CESMM (the model most Singapore civil BQs follow) measures excavation "net from the Drawings", "no allowance for bulking, shrinkage or waste", one m3 excavated = one m3 compacted fill, working space and overbreak not measured, disposal = excavation less compacted fill less imported fill. LTA M&W E/GD/09/104/A2 defines Suitable / Unsuitable (LL>70% or PI>50%) / Contaminated (SS 593) / Waste / Rock (>0.10 m3 boulders) classes that drive disposal cost, and requires a comprehensive level survey before any ground disturbance, which is the baseline surface for every later measurement.

Progress measurement is where the biggest QS-effort saving sits: RTK/PPK drone photogrammetry with GCPs reaches 1–3 cm horizontal, 2–5 cm vertical (Propeller's "1/10 ft" benchmark), Singapore vendors charge roughly S$1,500–S$10,000 per RTK survey depending on area (1–20 ha) with 2–3 day turnaround, platforms cost roughly US$4k/yr (DroneDeploy Flight & Analysis) or US$3,990/yr (PIX4Dmapper), and CAAS requires operator permit, UAPL pilot and per-site activity permits. A weekly or fortnightly surface, agreed jointly with the main contractor, replaces manual progress takeoffs with a computed surface difference; the daily-report load counts (loads × truck capacity × 1/bulking) and machine hours become a cross-check whose residual (fluff, bulking, part-loads, ±3–5% payload sensor error) is itself a KPI.
Key findings:
- [high] Average-end-area over-estimates earthwork volume by roughly 5–10% (a field example gave +6.8% over 25 stations); prismoidal corrects most of it; TIN/DTM surface-to-surface volumes are the most accurate when survey data is good.
- [high] LandXML surfaces are simple to parse (Pnts list with ids + Faces referencing ids) and open Python tooling exists: lxml for direct parsing, mac999/landxml_parser (alignments, cross sections, profiles to JSON/Excel), QGIS LandXml import plugin; point clouds via PDAL (Python bindings, JSON pipelines, LAS/LAZ) and Open3D; CloudCompare's 2.5D volume tool rasterises two clouds and sums per-cell height differences.
- [high] Civil BQ measurement convention (HK CESMM, the model widely followed in Singapore civil BQs): quantities computed net from the drawings, no allowance for bulking/shrinkage/waste; one m3 excavated is deemed one m3 compacted fill; excavation for structures measured as the volume the structure occupies plus the column above it to existing ground or earthworks final surface, whichever lower; working space, timbering and overbreak are contractor's risk and not measured; excavation items assigned to depth bands by maximum depth (not exceeding 3 m, 3–6 m, and so on in 3 m steps); disposal = volume excavated within site less compacted fill placed (less imported fill).
- [high] LTA M&W for Civil & Structural Works (E/GD/09/104/A2, Sep 2020) Chapter 4 classifies earthworks material into Top Soil, Suitable Material (compactable per Clause 4.12), Not Suitable Material subdivided into Unsuitable (clay with LL > 70% or PI > 50%), Contaminated (exceeds SS 593 intervention values, pre-existing) and Waste (debris, rubbish, logs, bentonite), and Rock (boulders > 0.10 m3 in trenches); Chapter 3 requires a comprehensive level survey of the contract area before any work that alters original ground levels; over-excavation of pits/trenches below specified levels is made good with grade 15 concrete at contractor's cost (Cl 4.7.3).
- [medium] Typical bulking (in-situ to loose) factors: clean sand/gravel ~14%, loam ~20%, dense clay/clayey gravel ~35%, very dense gravel-clay up to 50%, rock 30–40%; shrinkage (loose to compacted) ~5–10% for clay, 15–20% for rock. Bulking factor = volume after excavation / volume before; shrinkage factor = compacted volume / bank volume.
- [medium] Singapore staging-ground disposal fees (East Staging Grounds user manual, Aug 2022): Good Earth S$1.20/tonne, Soft Clay S$5.00/tonne before GST (soft clay fee includes the MPA dumping allowance); MPA designates offshore dumping sites for earth. Disposal is charged by tonnage at the staging ground, so the reuse/disposal split (Good Earth vs Soft Clay vs unsuitable/contaminated to licensed facilities) is a cost driver measured in tonnes, not m3.
- [medium] Drone photogrammetry accuracy with RTK/PPK plus GCPs: 1–3 cm horizontal, 2–5 cm vertical; research shows <1 GSD horizontal and <2 GSD vertical RMSE with RTK/PPK; bare-ground vertical RMSE ~0.15 m at 2 cm GSD in one 2024 study without dense control; GCP density guidance ~5–12 GCP/km2 with extra GCPs at edges and steep relief. Propeller's benchmark is '1/10 ft' (3 cm) with one AeroPoint; a 100-acre (40 ha) site flew in 23 min (Mavic 3E photogrammetry) or 26 min (M350 + Zenmuse L2 LiDAR) with ~10–15 h processing; LiDAR is needed under vegetation.

- [medium] Contour-to-surface from PDF/raster: for elevation rasters GDAL gdal_contour and QGIS Raster > Extraction > Contour go raster→vector; the reverse (scanned contour drawing → DEM) is still semi-manual: Bunting Labs' QGIS AI tracing plugin (Jan 2024) autocompletes lines you start on PDFs/GeoTIFFs; U-Net contour segmentation plus vectorisation post-processing is the 2025 research approach (ISPRS IJGI 2025 papers, including a study of how scan resolution/compression/bit depth degrade results), and an arXiv Dec 2024 paper addresses reconstructing broken contour lines during digitisation to build a DEM. - [high] Trench/pit excavation quantities are a formula over drawing objects the vector spike already extracts (run lengths, sump counts, labels): volume = Σ over runs of length × trench width × mean depth, where width = pipe/culvert outside width + contractual working space (often 300 mm each side or a table by pipe size in the BQ preamble), depth = ground level minus invert level minus bedding thickness taken at each sump/manhole and interpolated, then bucketed into depth bands by maximum depth; backfill = trench volume less pipe/structure volume; disposal = excavation less backfill reused. Manholes/sumps are measured as number (complete) with their own excavation either included or separately by depth range.

### Running an AI takeoff system from assist to autonomous-with-audit without losing accuracy: patterns from document AI, invoice/claims processing, medical coding, autonomous driving and construction estimating, with a staged framework for KKL's QS team
Every mature domain that has automated judgment work converged on the same shape: run the model silently beside the humans first (shadow mode), then let it draft while humans verify everything, then let it auto-accept only items whose calibrated confidence clears a per-class threshold while humans work the exceptions, then keep a random audit sample and drift monitors on the auto-accepted stream forever. Document AI vendors ship this as product: Rossum's default per-field auto-export threshold is 0.975, Microsoft tells customers to pilot first and derive their own straight-through-processing thresholds from observed confidence, and AWS A2I adds a "random sampling" activation condition specifically to audit the model regardless of confidence. Autonomous medical coding shows what graduation looks like at scale: Fathom reports ~95% encounter-level automation at 96-98% accuracy measured by client auditors, with low-confidence charts routed to humans, against an industry benchmark of 95% coding accuracy audited on roughly 25 charts per coder twice a year. Health-plan auto-adjudication benchmarks (~80% STP, best >85%) show that 15-20% of items staying with humans is normal, not failure.

The evidence also shows the two ways this goes wrong. First, automation bias: RCT evidence in medicine attributes ~45% of errors under AI assistance to over-reliance, explanations do not reduce it, and cognitive forcing functions (make the human commit before seeing the AI) do; EU AI Act Article 14(4)(b) now requires overseers be kept aware of automation bias. Second, deskilling: Budzyń et al. (Lancet Gastro Hep 2025) measured a 28.4% to 22.4% fall in endoscopists' unassisted adenoma detection after months of AI use. Construction-specific evidence is thin but pointed: the only independent studies of an AI takeoff tool (Togal) found counts near-perfect (11/13 identical to the contractor) while area quantities were systematically under-measured (12/15 items low, p=0.027) and worst on complex geometry, i.e. graduation must be per item class, not per tool. Vendor 97-98% accuracy claims are unverified.

For KKL this maps onto a five-stage, per-class programme. Stage 0 instruments the current workflow (timer per sheet per activity code, two-QS agreement baseline). Stage 1 shadow-runs the engine on every sheet the QSs already measure, blind, for at least ~200 items per class across several projects and both vector and scan sources. Stage 2 lets the AI draft with QS verifying every item (each edit logged as a label). Stage 3 auto-accepts per class above a calibrated threshold, with a 10% random audit decaying to 2-5%, a value-based always-check rule, and hard rollback triggers (any money-bearing error in the auto-accepted stream, audit error rate doubling, unfamiliar drawing source, any model/prompt change). Stage 4 is autonomous-with-audit; a named QS still signs, because under PSSCOC Option Module A quantities are measured and certified as variations and the contractor's own pricing and claim quantities carry the contractor's risk. Effort reduction is proven with logged minutes per sheet per class, not self-report.
Key findings:
- [high] Shadow deployment (run the model on live inputs, log its output, serve nothing) is the standard first stage for promoting an ML model, and its purpose is to compare against the incumbent (here, the human QS) on the same live data before anyone relies on it.
- [high] Confidence-gated routing is productised in document AI with concrete defaults: Rossum auto-exports a field when its score exceeds a per-field/per-queue threshold (default 0.975); Microsoft recommends piloting to derive STP-vs-human thresholds and targets 80%+ model accuracy generally and 'close to 100%' for financial/medical; AWS A2I lets you trigger human review on per-key confidence, on a missing important key, or by random sampling for audit.
- [medium] Autonomous medical coding is the closest analogue to money-bearing takeoff at scale: engines route sub-threshold cases to humans, publish automation rate and audited accuracy separately, and the industry benchmark is 95% accuracy verified by periodic chart audits.
- [medium] In insurance claims, auto-adjudication (straight-through) rates of ~80% are the benchmark and >85% is best-in-class; 15-20% of items remaining with humans is the expected steady state, not a failure of automation.
- [high] Independent evidence on AI takeoff tools shows accuracy is class-dependent: counts are near-perfect, areas are systematically under-measured, and complex geometry is worst; therefore graduation must be per item class and per drawing type, and vendor 97-98% claims are unverified.
- [high] Automation bias is large and measurable, explanations do not fix it, and cognitive forcing functions (make the human commit before seeing the AI, or hide the AI answer on a sample) do reduce over-reliance; the EU AI Act now codifies awareness of automation bias as a human-oversight requirement.
- [high] Deskilling from routine AI assistance is now documented in a real-world clinical setting: experienced operators lost unassisted skill after months of AI use, so a takeoff programme needs deliberate skill-maintenance (unassisted reps, blind audits) especially for the QSs who will be the reviewers of last resort.
- [medium] Learning from corrections is the standard mechanism for improving automation rate over time: every human edit becomes a label, low-confidence items are prioritised for human labelling (active learning), and a handful of labelled examples of a new variation is enough to retrain a document model.
- [medium] Drift monitoring practice: alert on the joint condition of input drift plus a measured accuracy drop, use PSI-style heuristics (0.1 attention, 0.2-0.25 action) as starting points calibrated per feature, and never roll back without verifying the previous version is not subject to the same failure mode.
- [high] Under Singapore public-sector contracts, BQ quantities are expressly 'estimated' and differences are measured and valued as variations at BQ rates by the Superintending Officer; the contractor's own takeoff errors therefore bite in tender pricing (rates, resourcing, lump-sum or D&B scope), in progress-claim and VO quantities it submits for certification, and in subcontractor payment measurement; sign-off must stay with a named QS.
- [low] Baseline effort figures for takeoff are only vendor-sourced: estimators reportedly spend 40-60% of their time on manual takeoff and up to ~90 minutes per drawing sheet; the Togal peer-reviewed study is the only measured time comparison (~71% saving on architectural plans, single user). KKL must measure its own baseline rather than adopt these.
- [high] KKL's existing assets already implement several prerequisites: verify-before-use states (DR Verify), a corrections log, a planned evaluation set with published accuracy targets (95% Ask/Check, 98% cell accuracy on Extract), audit log of who ran what, and activity codes (EW-EXC m3, DR-PIPE m, RW-KERB m, RC-CONC m3) that can serve as the item-class taxonomy for per-class graduation.

### Singapore measurement standards, BQ formats and data availability that shape what a KKL takeoff system can automate
Singapore has no national civil-engineering standard method of measurement. The only nationalised SMMs are SISV SMM2 (building works, 1986), re-issued as Singapore Standard CP 97-1:2002 (CEMS Part 1, confirmed 2015) and CP 97-2 (M&E). CEMS was explicitly written so that software could extract quantities electronically from object-oriented CAD and present them as BQs, but it covers building trades, not earthworks/drainage/roads as civil works. Public-sector civil BQs are therefore governed by contract-specific preambles: PSSCOC 2020 Option Module A clause A3.0 says works are measured per the Preambles to the BQ; HDB's Standard Schedule of Rates carries General and Particular Preambles per trade (Part 4 Earthworks, Part 9 Storm Water Drainage) and, per a secondary source, deems its BQ prepared under CESMM (UK). A real statutory-board schedule (Sentosa FSOR) shows the shape KKL's QSs meet daily: excavation in m3 measured nett with bulking and planking in the rate, banded by depth (n.e. 2 m, 2-4 m, 4-6 m); trench excavation per m by depth band with backfill and disposal included; precast channels per m by type with excavation measured separately; road layers in m3/m2 at consolidated thickness; disposal per m3 with bulking in the rate.

PSSCOC Module A makes quantities "estimated": differences found on measurement of work actually executed are variations valued at BQ or analogous rates (cl. 20.1(a)/(b)); provisional quantities are remeasured at completion; failing that, fair market rates or cost plus 15%. Progress payment is claim-driven (cl. 32.1) under the SOP Act, which requires every dollar to be calculated by reference to the contract and work done, with fixed response windows.

Data availability: LTA publishes tenders exclusively on GeBIZ; documents are PDFs and ZIPs ("Tender Schedule.zip", "Price Schedule.pdf"), with NDA-gated passwords for sensitive contracts and mandatory electronic submission of price and technical documents. There is no public evidence that DWG or IFC is issued to tenderers. CORENET X (mandatory 1 Oct 2025 for GFA ≥30,000 m2, 1 Oct 2026 for all new projects) and its IFC+SG BIM requirement (GFA ≥5,000 m2) are framed around building works by GFA, so civil earthworks, drainage and road contracts are outside its practical scope. LTA is ISO 19650-certified with an InSIGHT CDE, so rail main contractors hold BIM, but subcontractors such as KKL receive derived PDFs/DWGs. Confidentiality is governed by the Official Secrets Act (documents and drawings), the Infrastructure Protection Act for rail facilities, LTA NDAs, and agency rights to require local hosting or clearance for sensitive data. Digital site platforms (Novade on 40+ LTA and 100+ HDB projects) handle diaries and progress but no standardised e-measurement was found; joint measurement remains a contract-practice, spreadsheet-based activity.
Key findings:
- [high] Singapore's nationalised measurement standards (SISV SMM2 → SS CP 97-1:2002 CEMS Part 1, confirmed 2015; CP 97-2:2004 for M&E, reaffirmed 2020) cover building and M&E works only; there is no Singapore Standard SMM for civil engineering (earthworks, drainage, roads). CEMS was designed for automatic quantity takeoff from object-oriented CAD.
- [high] PSSCOC for Construction Works 2020 (8th ed.) Option Module A makes BQ quantities estimates, sends measured differences through the variation mechanism at BQ or analogous rates, remeasures provisional quantities at completion, and defers the method of measurement to the BQ Preambles.
- [high] A Singapore statutory-board schedule of rates (Sentosa Development Corporation term contract FSOR) shows the concrete item logic for earthworks, drains and roads: prepared 'in accordance with the principles of' SISV SMM2 with contract-specific departures; excavation measured nett with bulking, planking/strutting and dewatering deemed in rates; m3 items banded by depth; trench items per m by depth band with backfill and disposal included; precast channels per m by type with excavation measured separately; disposal per m3 'rate include bulking'; road layers by consolidated thickness in m3/m2.
- [medium] HDB's Standard Schedule of Rates carries General Preambles (measurement standards and rate inclusions) plus Particular Preambles per trade, with civil work classified into Parts including Part 4 Earthworks and Part 9 Storm Water Drainage Network; a secondary source states the HDB BQ is deemed prepared under CESMM (the UK Civil Engineering Standard Method of Measurement).
- [high] LTA tenders are published and documents distributed exclusively via GeBIZ as PDFs and ZIP bundles; price schedules are PDFs; sensitive contracts require a signed NDA before a download password is issued; price and technical documents must be submitted electronically on GeBIZ. No evidence that DWG/DXF or IFC models are issued to tenderers.
- [high] CORENET X and IFC+SG mandates are scoped to building works by GFA (CORENET X mandatory 1 Oct 2025 for new projects ≥30,000 m2 GFA, 1 Oct 2026 all new projects, 1 Oct 2027 ongoing projects; BIM/IFC+SG submissions only for GFA ≥5,000 m2), so they do not deliver BIM models for stand-alone civil earthworks, drainage or road contracts.
- [medium] LTA runs an ISO 19650-certified BIM programme (Parts 1, 2, 3 and 5) with the InSIGHT common data environment (FulcrumHQ) on rail projects such as Jurong Region Line and Cross Island Line; deliverables are information-rich BIM models, sheets (drawings) and spatial data. These sit with LTA and main contractors, not subcontractors.
- [medium] Progress claims are statutory under the SOP Act 2004 (in force 1 Apr 2005): claimant must show every dollar is calculated by reference to the contract and work actually performed; respondent has a fixed window to respond, after which the claim is deemed accepted. PSSCOC cl. 32.1 Payment Claims and cl. 20.2(2)(a) route measured work and variations into these claims.
- [medium] Client drawings for public-sector civil works are confidential under the Official Secrets Act 1935 (covers documents, drawings, photographs), LTA NDAs for password-gated tenders, and the Infrastructure Protection Act 2017 for protected places such as MRT depots; public agencies may require local hosting and security clearance for handling sensitive data. This constrains sending drawings to third-party cloud AI.
- [high] buildingSMART Singapore's Measure Work Group is the live body for BIM-based measurement; it maintains CEMS (CP 97-1/-2), is exploring 'e-Phraseology' (standard item descriptions) and CAD measurement training, but has published nothing for civil infrastructure quantities or IFC-SG quantity takeoff.
Implications:
- Measurement rules must be contract-driven, not standard-driven: the system should ingest each tender's General and Particular Preambles (PSSCOC A3.0 makes them binding) and turn them into machine-checkable rules per item class: nett vs bulked volumes, depth bands (e.g. n.e. 2 m / 2-4 m / 4-6 m), working space and planking deemed included, trench length 'measured over sump pits', excavation for channels measured separately or included. Start with a rule template per client (LTA, HDB/SOR, PUB, JTC) and let QSs confirm deltas per tender.
- Geometry-to-BQ mapping is viable because public-sector civil BQ items are regular in shape (unit + size/depth band + inclusions): m3 excavation by depth band, m trench by depth band, m pipe/drain by diameter/type, no. sumps/manholes by depth, m2/m3 pavement layers at consolidated thickness, m3 disposal. Build a KKL item library keyed on (trade, unit, band, inclusions) learned from historical priced BQs; classify new BQ lines into it with an LLM plus QS confirmation, then bind measured geometry to library items.
- BQs will arrive as PDF price schedules inside GeBIZ ZIPs, not Excel/XML: invest in a PDF-table-to-structured-BQ parser (item no., description hierarchy, unit, quantity, rate) with page references; treat Excel as a bonus when the main contractor supplies it.
- Vector-first is viable but PDF-first is mandatory: LTA/HDB/PUB issue PDF drawings via GeBIZ; DWG/IFC are obtainable only on request from the client or, on rail subcontracts, from the main contractor's ISO 19650 CDE. Keep the vector-PDF path as the primary channel, DXF as a fast path when supplied, and 300 dpi raster fallback for scans and legacy as-builts. CORENET X/IFC+SG will not change this for civil contracts in 2026-2027.
- Remeasurement is where the money is: under PSSCOC Module A, payment follows measured executed work and variations valued at BQ/analogous rates, so the same item mapping used at tender must be reused for progress claims and VOs. Pair drawing-based takeoff with as-built survey volumes (GNSS/drone DTM differencing) so claimed m3 tie to BQ items with an audit trail suitable for SOP Act claims and adjudication.
- Design for confidentiality tiers: run all geometry extraction and measurement locally (this is already how the PyMuPDF/ezdxf spikes work); send only non-sensitive text (BQ line descriptions, preambles, spec clauses) to the Claude API; for NDA-gated LTA/rail drawings, require explicit client consent or an on-prem/approved-cloud deployment before any drawing content leaves the company. Tag every project with its NDA status at intake.
- Because no external civil measurement taxonomy exists in Singapore (CEMS is building-only, CESMM is referenced by HDB but not nationalised), KKL's daily takeoffs are the only training corpus: capture every QS takeoff as (drawing region, measured geometry, preamble rule applied, BQ item, quantity) and use accuracy against the QS's final figure as the promotion criterion for automating each item class.
- Accuracy targets should be item-class-specific and framed against remeasurement tolerances: exact for vector PDF/DXF lengths and counts (drains, pipes, sumps), ~2% for scanned plans, and explicit uncertainty for volumes that depend on spot-level interpolation ('constant gradient between spot levels' rule) and depth-band allocation.
