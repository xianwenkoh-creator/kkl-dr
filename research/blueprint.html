Recommendation

Build the document workbench. Buy the measured takeoffs, for now.

WHAT TO DO
  • Build now. An internal tool where staff drop tender and project PDFs and run five agents on them: Ask, Check, Extract, Compare, Takeoff assist. Every answer cites the page it came from. A working prototype is in the repo at ai/index.html.
  • Buy or outsource. Measured areas, lengths and volumes from drawings. Civils.ai still puts its own engineers between the model and the customer for these; KKL's estimators already have tools. Revisit in Phase 3.
  • Do what civils.ai cannot. Point the same agents at KKL's own data: the machine register, DR Capture rows, soil and disposal streams, idle reasons, diesel, subcons.
  • Budget. About US$800 a month in model usage for ten pilot users, US$2.5k at thirty; hosting US$100–300 a month from Phase 1; development in-house.
  • Guardrails. Citations on every answer, a verify-before-use step like DR Verify, a per-project upload rule signed off by contracts, and an evaluation set so KKL measures its own accuracy.

2022 to 2026

How the product moved, and what that tells us

  1. 2022: geotechnical AI. Free calculators and a borehole-log digitiser; mapping city geology from public records.
  2. 2023–24: a document platform for AEC. Search, cited Q&A, compliance checks, contract review, a no-code workflow builder. Consultancies and JTC adopt it; pay-as-you-go from about US$5 a document.
  3. 2025–26: takeoffs and checks for contractors. The homepage leads with measured quantities from PDF drawings, QA-reviewed by their engineers, and names the earthworks contractor as the customer.

Document question-and-answer became table stakes as frontier models learned to read PDFs and cite pages natively, so civils.ai moved to a verified, per-unit deliverable. That deliverable is software plus people: results come back in a day, not seconds. Two lessons for KKL: the cited-answer layer is now cheap to build, and fully automatic measured takeoffs are still not reliable enough to ship without a human, even for a specialist team.

Implications

What this means for KKL

The cheap 80%

Ask, Check, Extract and Compare with page citations are what a frontier model does out of the box today on a 600-page PDF. This is product work, not AI research, and it fits the single-file style of DR Capture and the SKYTOPIA apps.

The hard 20%

Measured takeoffs need scale detection, vector geometry, classification of hatches and lines, and a person to confirm. Start with counts and schedule reads the model does well; keep measured quantities with existing estimating tools or buy them per sheet.

KKL's edge

A register of 1,421 machines (203 × 14 t excavators, 120 × 35–40 t, 100 × 20 t, 108 rollers), daily-report rows per activity code (EW-EXC, DR-PIPE, RC-CONC…), soil type and disposal stream, idle reasons, diesel and subcon records. “Ask the daily reports” is a KKL-only feature no vendor can offer.

Product definition, v1

The five agents

AgentInputOutputModel features
AskDocuments and a questionCited answer; each citation opens the pagePDF input with page citations
CheckDocuments and a checklist, saved as a templateTable: item, Pass / Fail / Unclear / Not found, evidence with citations, notesCitations; templates per authority and document type
ExtractDocuments and a column list or presetTable with a page reference per row; CSV downloadJSON-schema structured output
CompareTwo or more documents and criteriaOne column per document, one row per criterion; differences and gapsJSON-schema structured output
Takeoff assistDrawings and a scopeCounts and schedule reads with sheet, basis and confidenceStructured output; explicitly no measured geometry until Phase 3

Non-negotiable in the interface: no citation, no answer; a visible “checked by” step before export, as in DR Verify; a cost readout after every run; CSV, Excel and Markdown export, and later a save to the project's SharePoint folder. Not in v1: measured takeoffs, cut and fill, drawing mark-up, BIM, cross-project chat memory, or anything that acts without a person reviewing.

Architecture

Four phases, one setting for the model

Phase 0, in the repo now

A single file, hosted on GitHub Pages like DR Capture. The browser calls the model API with the user's own key, documents are sent as PDF blocks with citations enabled and marked for prompt caching, structured agents use a JSON schema, pdf.js renders the cited page in a side panel, and runs are kept in the browser. Good for proving value on a live tender and agreeing the checklist templates. Not for shared use, large drawing sets or an audit trail.

Phase 1, weeks 3 to 8

One container on Azure (KKL runs Microsoft 365 and SharePoint), Blob for documents, Postgres for projects, runs, results and citations, Entra ID sign-in, a job queue with streaming progress, templates with named owners, and a SharePoint connector that reads a project folder and writes exports back. Documents are uploaded once to the Files API and referenced by ID; bulk checks go through the Batch API overnight.

Phase 2, weeks 9 to 16

A reusable spec library; “Ask the daily reports” over DR Capture, DR Verify and the machine register; SI report to soil profile to expected disposal streams per zone; claims assembly from DR rows, instructions and clauses.

Phase 3, only after daily use

Vector geometry from drawings, scale from the title block, a light measurement interface where the model proposes and the estimator confirms, cut and fill from levels. Or keep buying it per sheet if the volume does not justify the build.

Rules

Confidentiality, accuracy and trust

Client documents

  • LTA, HDB and PUB documents often carry confidentiality clauses. Contracts confirms what may be processed by a third-party service before anything is uploaded, to civils.ai or to KKL's own tool.
  • A per-project “may upload / may not upload” rule, kept with the project file.
  • Commercial API terms do not train on inputs and retain data for a limited period; record the terms.

PDPA and residency

  • Safety and HR documents carry personal data; keep them out of v1 or redact first. Crew counts are fine, crew names are not needed.
  • If a client requires data to stay in Singapore, run the same model through a cloud region that offers it, subject to model availability; the endpoint is one setting.
  • Entra ID sign-in, project-level access, an audit log of who ran what on which documents.

Accuracy

  • Citations are the product. Check must say “Not found” rather than guess.
  • An evaluation set from three past tenders: 50 questions with known answers, two checklists with agreed results, three schedules with the correct Excel. Score every prompt and model change against it.
  • Results are drafts until initialled. Money-bearing quantities never leave without a named checker.
  • A corrections log: every user override is kept and becomes next quarter's test set.

Pilot

Twelve weeks

  1. Weeks 1–2 · Prototype in use. Three people (tender, one PM, one QS) on one live tender. Done when 30 real prompts have run, three checklist templates are drafted, and the first cost readout is on the table.
  2. Weeks 3–4 · Service skeleton. Sign-in, projects, upload once, run, results with citations. Done when two projects are loaded and the same prompts answer from the service.
  3. Weeks 5–6 · Templates and exports. Extract presets, CSV and Excel export, SharePoint write-back. Done when the tender team runs the risk checklist on every new tender.
  4. Weeks 7–8 · Measure. Evaluation set built and scored; accuracy and cost dashboard. Go or no-go for wider rollout.
  5. Weeks 9–12 · First Phase 2 slice. Spec library and “Ask the daily reports” over DR Capture CSVs. Done when the plant department answers one weekly question from it.

Team: the in-house builder part-time, one tender manager and one QS as owners of the templates, one contracts person for the upload rules. No new hires.

In the repo

The prototype

ai/index.html is a working Phase 0: add PDFs, text or CSV files; pick Ask, Check, Extract, Compare or Takeoff assist; insert a template (tender risk checklist, method statement review, subcon quote review, borehole strata, drainage schedule, sheet index); run. Answers stream in with page chips that open the cited page; Check verdicts colour-code Pass, Fail, Unclear and Not found; Extract, Compare and Takeoff assist come back as tables with CSV download; every run shows tokens and an estimated cost; a “Mark checked” step stamps initials before export. Settings hold the API key (this browser only), model, effort and output length.

To try it: open the page from GitHub Pages once the branch is merged, or open the file locally, put an API key in Settings, load one tender's spec and drawings, and run the tender risk checklist. Scanned drawings without a text layer are read visually but cannot be page-cited, and measured quantities are deliberately out of scope.
